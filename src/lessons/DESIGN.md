# 授業と教科書の設計書（作り直し版）

初心者でも理解できる授業と教科書に、一から作り直すための設計書。
新しい回を作るとき・直すときは、この設計書に従う。問題づくりのルールは `src/questions/INSTRUCTIONS.md`。

## 0. 決まっていること
- 作り直すのは**授業（台本・音声）と教科書の両方**。
- **1回は約12〜15分**。そのぶん回数を増やす（50回 → 81回の予定）。
- **授業中に何度も止まって確認の問題を出す**（かたまりごとに1問。アプリも対応させる）。
- 問題・教科書・台本はすべてオリジナル（CLAUDE.md の大事なルールのとおり）。

## 1. 誰のための授業か
- **ネットワークの知識がゼロの人**。パソコンとスマホは使えるが、IPアドレスという言葉も知らない。
- 通勤中などに**音声だけで聞いても**わかること。画面（教科書の図）は理解を助けるもので、図がないと意味が通じない話し方はしない。

## 2. 1回の授業の型

| 順番 | 中身 | 目安 |
|---|---|---|
| ① つかみ | 身近な場面・困りごとを1つ（例：「会社のWi-Fiだけつながらない」）。いきなり用語の定義から入らない | 1分 |
| ② 今日のゴール | 「終わったらできること」を**3つまで**言う | 30秒 |
| ③ 本編 | **かたまり 2〜3個**。かたまりごとに、最後に**確認の問題**で止まる | 8〜10分 |
| ④ まちがえやすい所 | 生徒がよくある誤解を言い、先生が「惜しい、実は…」と直す | 1〜2分 |
| ⑤ まとめ | 3行で言い直す＋次の回とのつながり（「次は、この住所をどう分けるかです」） | 1分 |

本編の進め方は、回の「形」（4章）に合わせる。

## 3. 台本を書くルール
1. **困りごと → 生徒が考える → 先生が直す → 最後に用語の名前**の順に話す。
   - 悪い例：「VLSMは可変長サブネットマスクです。必要なホスト数に合わせて…」
   - 良い例：「100台の部署と2台の線、同じ大きさで分けたら？」→ 生徒が考える →「必要な大きさごとに分ける。これがVLSMです」
2. 新しい用語の数に制限は設けない。ただし用語は**意味を説明してから名前を出す**。1回の中で用語を並べるだけにならないよう、1つずつ「何のためのものか」まで話す。
3. **まだ習っていない用語を使わない**。使うなら、その場で一言で説明する。各回の「前提の回」（5章）より後の内容は出さない。
4. **先生の1行は1つのことだけ、40字以内を目安**にする（今の版は平均70字で、耳で追えなかった）。
5. **生徒は完全な初心者**として話す。素朴な疑問を言い、よくまちがえる。相づちだけの行（「覚えました！」）を続けない。生徒の行は全体の**3割以上**にする。
6. **「なぜ」を必ず言う**。「〜します」で終わらせず、「〜しないと、…で困るから」まで言う。
7. **たとえ話は、本物の言葉に戻すところまで**話す（「郵便番号のようなもの」で終わらせない）。
8. 確認の問題の前は「ここで考えてみてください」と言い、答えの前に間を置く。
9. 読み上げで誤読しやすい語は、今までどおり `y`（読み）を付ける。略語は初出で正式名を言う。
10. **淡々とした説明を避ける**（7章の書き方を、台本でも守る）。

## 4. 回の「形」（本編の進め方）
分野ごとに基本の形を決め、合わない回だけ別の形にする。

| 形 | 使う所 | 進め方 |
|---|---|---|
| **たとえ話** | 入門 | 身近なもの（郵便・住所・建物）に置きかえてから、本物の言葉に戻す |
| **一緒に解く** | 基礎の計算（2進数・サブネット・IPv6） | 生徒が手順を声に出して解き、つまずいた所を先生が直す。最後に「自分で解いてみて」と問いかける |
| **実況中継** | アクセス（スイッチ・STP・VLAN） | フレームやBPDUを主人公にして、スイッチの中で何が起きるかを1つずつ実況する |
| **パケットの旅** | IP接続（ルーティング・OSPF） | パケットの目線でルーターを進み、各ルーターでルート表を一緒に読む |
| **困りごと相談室** | IPサービス（NAT・DHCP・NTPなど） | 現場の相談から始め、そのサービスで解決する |
| **事件簿** | セキュリティ | 攻撃の場面を物語で見せ、「どこが弱かった？」「どう防ぐ？」を考える |
| **手作業 vs 自動化** | 自動化 | 「200台に1台ずつ設定」の大変さから入り、ツールで解決する。JSONなどは実物を一緒に読む |
| **トラブル解決** | 設定・コマンドの回 | 動かない設定を見せて、show の出力から一緒に原因を探す |
| **対決** | 用語を比べる回 | 2つを並べて「どっちのこと？」と当てさせる |

## 6. 教科書の作り方
- **ページ数に制限は設けない**。わかりやすさを優先して、必要なだけページを使う。
- 授業で話している所のページ（図）が画面に出るように、授業の各行にページを対応させる（`sc`）。1つのかたまりが何ページにまたがってもよい。
- ページの並びは授業の流れに合わせる：つかみ → 本編（かたまりごとに確認の問題のページ）→ まちがえやすい所 → まとめ。
- 教科書は、授業を聞いたあとの**見直し用**でもあり、**教科書だけ読んでも理解できる**ようにする。
- 図の中の文字は日本語でよいが、端末の出力（等幅）の中は英数字だけにする（日本語は幅がそろわない）。

## 7. 淡々とした文章を避ける書き方（授業・教科書の両方）
今の版がわかりにくかった一番の理由は、事実を並べるだけの淡々とした文章だったこと。次のように書く。
- **読み手に話しかける**：「〜です。〜します。」を続けず、「もし〜だったら、どうなると思いますか？」「ここが大事なところです」のように語りかける。
- **事実の前に「困ること」を書く**：「ARPはIPアドレスからMACアドレスを調べます」ではなく、「住所（IP）はわかっても、届けるには相手の顔（MAC）が要ります。そこで…」。
- **具体的な場面を入れる**：機器名・アドレス・人を出して、場面が目に浮かぶようにする（「営業部のAさんのPCが…」）。
- **理由を必ず書く**：「〜します」で止めず、「〜しないと…で困るから」まで書く。
- **ひと息つく言葉を入れる**：「ちょっと難しく感じたら、ここだけ覚えておけば大丈夫」「ここまでで半分です」。
- **まちがえやすい所は、まちがいから見せる**：「よくある勘違いが〜。実は…」。
- 教科書の本文も、箇条書きの羅列だけにせず、短い文章で流れを作る。要点は「ポイント」（`p`）にまとめる。

## 9. 品質の確かめ方
自動チェック（check.py に足す）：
- 先生の1行が長すぎないか（60字を超えたら警告、40字が目安）
- 生徒の行が3割以上あるか
- `terms` が用語集にあるか
- まだ習っていない回の用語（`need` より後の回の `terms`）を台本で使っていないか
- 確認の問題の数と `w:1` の数が合っているか

## 10. 進め方
1. **試作**：性質の違う3回を作る（第1回 たとえ話、第19回 一緒に解く、第50回 トラブル解決）。台本・教科書・確認の問題まで作る。
2. 読んで・聞いてもらい、型やルールを直す（この設計書も更新する）。
3. アプリを対応させる（何度も止まる授業、新しい回の項目、問題と回の対応）。
4. 残りの回を分野ごとに作る。音声はまとめて作る。
5. **全回ができてから、新しい版に切り替える**（回番号が全体で変わるため、途中で一部だけ入れ替えない）。それまでは今の版を公開したままにする。
